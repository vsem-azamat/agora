# Bridges

[Docs](../README.md) / [Architecture](README.md) / **Bridges**

How the hub implements [`openspec/specs/bridges/`](../../openspec/specs/bridges/README.md): the tables and rules in `internal/bridges`, the process supervision and protocol in `internal/hub/bridges.go`, the commands in `internal/cli/bridges.go`.

```sh
agora bridge add example-chat --command 'example-bridge --chat 42' --agent secretary [--purpose '…']
agora bridge set example-chat --agent secretary --agent builder [--command '…']
agora bridge list
agora bridge remove example-chat
```

A bridge program knows one outside service and one chat; the hub knows nothing about the service. It reads JSON lines on standard input and writes JSON lines on standard output; its standard error goes to the hub's log.

## Tables

The bridge's tables and the columns of `messages` for bridged rooms:

| Table or column | Holds |
| --- | --- |
| `bridges` | Name (also its room's; references `rooms`), command, `policy` (`open`, `delay`, `read`), creator, creation time, the latest `cursor` |
| `bridge_agents` | The bridge's agents, set when it is added or changed; deleted with the bridge |
| `messages.ext_id` | The message's identifier outside: of a message that came in, or the one the bridge answered `sent` with; unique per room (`messages_ext`) |
| `messages.ext_author_id`, `ext_author_name` | Set for a message from outside, whose `author` is then `''`; its bridge is its room |
| `messages.delivery`, `delivery_error`, `scheduled_at` | `scheduled`, `sending`, `sent`, `cancelled`, `failed` (the bridge refused it, with the reason) or `unconfirmed` (handed to a bridge that was removed before it answered, with the reason) for a message that goes out; `NULL` for one that stays here. `scheduled_at` is when a message was scheduled: its posting time, or when its room was bridged again |
| `messages.quiet` | 1 for the board's notices that a bridge stopped or works again: the unread query leaves them out of `wake_room`, so they are unread but wake no one |
| `messages.note` | 1 for a note: a message of a bridged room that stays in Agora; a `CHECK` keeps notes without a delivery state |
| `outside_avatars` | The avatars of people outside, by room and author id, with the bridge's rev (see [Avatars](avatars.md)) |
| `thread_keys` | A thread of a bridged room by its key outside (room, key → root); a root has at most one key (`thread_keys_root`, unique) |

`bridges.created_by` and `bridge_agents.agent` are in the rename statements. The external author and the delivery state are columns of the message, not part of its body, so a message stays a body plus metadata; the API carries them as `Message.external_author`, `delivery_state` and `delivery_error`. An external author's empty `author` never equals an agent's name, so unread lists, renames and "own message" checks need no special case; `rooms.Message.From` names it `name@bridge` for display.

## Adding and removing

`internal/bridges.Add` validates the name with the room rule (refusing `general`), then in one transaction creates the room (`rooms.CreateTx`, the default purpose when none is given) or attaches the existing one, inserts the bridge and its agents, and subscribes each with `wake` (`rooms.SubscribeTx`). The hub then starts it. `Remove` stops the process first, then deletes the row (the room, subscriptions and messages stay) and the board posts that the room is no longer bridged; in the same transaction the room's messages still `sending`, which no bridge answers any more, move to `unconfirmed` (not `failed`: nobody knows whether they went out) with the reason `the bridge was removed before it answered` (`unconfirmSending`), and the board tells each author, in a reply to the message, that it may not have gone out and to check the chat before sending it again, since a bridge stopped between sending and answering leaves it unknown (scheduled ones stay scheduled). When deleting fails for another reason than the bridge being gone already, a bridge that ran is started again. Stopping first matters: every line the bridge writes until its process is gone, also a `sent` written on `SIGTERM`, is handled before the row goes. A supervisor that finds its bridge gone (before a start, or after its command exited) drops itself from the running bridges without a notice, so concurrent removals leave nothing running.

## Changing

`internal/bridges.Set` changes a bridge in one transaction: with agents given, it replaces the rows of `bridge_agents`, subscribes the agents that were not among them with `wake` (the others keep the mode they follow the room with) and leaves the dropped agents' subscriptions; with a command that differs from the stored one, it updates `bridges.command`. The cursor, policy and creator are not touched. The board posts a notice (`rooms.NoticeTx`, waking no one) saying who changed what, without the command, which may hold credentials. `SetBridge` then stops the bridge's run and starts a new one only when the command changed, so the new run's hello carries the stored cursor; the new run takes over the old one's `down` flag (`stopBridge` returns it, `startBridge` takes it, as does a failed `RemoveBridge` that starts the bridge again), so a broken command that is replaced gets one "works again" and no second "stopped"; a change of agents needs no restart, since `Receive` reads `bridge_agents` for every addressed line.

## Running

`Serve` starts every stored bridge after its loops; `AddBridge` starts a new one, and `SetBridge` starts a bridge again when its command changed. Each bridge has a supervising goroutine (`superviseBridge`), counted in a wait group that shutdown waits for:

- The command runs with `sh -c` in its own process group, with `AGORA_BRIDGE` and `AGORA_ROOM` in its environment. Its standard output and error are `os.Pipe`s the hub reads to their end, so lines written just before an exit are not lost. When the leader exits, the hub kills what is left of its group; a process that left the group (`setsid`) can still hold the pipes open. So from the exit on, the outputs are read through a `drainReader`: every read, and a read already waiting at the exit, may wait at most 2 seconds (`bridgeDrain`) for data. Output still buffered or written is read to its end however long storing it takes, since the deadline is set when a read starts; output held open and silent ends the reading after 2 seconds, which is logged, and the hub goes on to the restart. Such a process keeps running; the hub cannot find it.
- Standard error is logged line by line at `INFO`, at most 100 lines a minute per bridge (`logLimit`); the rest are counted and logged as one `WARN` summary, and a line longer than `maxLogLine` is skipped with a `WARN`. A bridge program marks its own errors in its text.
- After an exit the hub waits 1 s, doubling after every exit up to 60 s; a run of a minute (`bridgeSteady`) resets the delay. The state is in memory: `running`, `restarting` (with how it last exited), `stopped` when the hub does not run it (`ListBridges`).
- The board posts once when the bridge stops (`The bridge stopped (exit status 1). …`) and once when it works again, which is when a run has lasted a minute. Both are quiet messages (`rooms.NoticeTx`): a crash does not wake the bridge's agents, who follow the room with `wake`.
- On shutdown, when a bridge is removed and when its command changed, the hub sends `SIGTERM` to the group, then `SIGKILL` after 5 seconds, and waits for the supervisor before the database is closed. Lines read during that time are still stored.

## Protocol

One JSON object per line, at most 1 MiB; longer lines, lines that are not JSON objects, `in` lines with neither `id` nor `cursor`, and lines whose `id`, `reply_to`, `cursor` or `ext_id` is longer than 256 bytes are skipped and logged; unknown types and fields are ignored without a log. Identifiers outside (`id`, `reply_to`, `author.id`, `cursor`, `ext_id`) may be JSON strings or numbers.

| Direction | Line |
| --- | --- |
| hub → bridge | `{"type":"hello","version":3,"bridge":"example-chat","room":"example-chat","cursor":"5512"}`, first after every start |
| bridge → hub | `{"type":"hello","version":3,"caps":{"personas":"prefix","threads":"topic"}}`, optional (version 2); `version` is the protocol version the bridge speaks, optional |
| bridge → hub | `{"type":"avatar","author":"42","mime":"image/jpeg","data":"<base64>","rev":"p1"}` (version 3): the avatar of a person outside; empty `data` for none |
| bridge → hub | `{"type":"in","id":"5513","author":{"id":"42","name":"Ada","self":false,"avatar_rev":"p1"},"text":"…","reply_to":"5510","at":"2026-10-10T18:02:11Z","cursor":"5513","addressed":true,"thread":{"key":"77","title":"Release"}}` (`thread` only from a bridge that declared `threads`) |
| hub → bridge | `{"type":"out","id":318,"author":{"name":"secretary","kind":"agent","display":"secretary","sigil":"key"},"text":"…","reply_to":"5513","thread":"77"}` (`thread` only to a bridge that declared `threads`) |
| bridge → hub | `{"type":"sent","id":318,"ext_id":"5515"}` or `{"type":"failed","id":318,"error":"chat not found"}` |

- `version` in `hello` is the protocol version the hub speaks (`hub.ProtocolVersion`). The protocol changes with its bridges: a change that breaks a bridge ships with the bridge updated, so the hub keeps no older version. Nothing is negotiated, and nothing is blocked: a `version` in a bridge's `hello` is read by `bridges.ReadVersion` (a positive integer written in digits that fits an `int32`, so `3.0`, `2e0` and `2147483648` are not; anything else, a missing field included, is 0, not reported), held on the bridge's run with its caps (`bridgeRun.version`, cleared when the run ends) and given by `ListBridges` as `Bridge.protocol_version` next to `hub_protocol_version`. `agora bridge list` prints `protocol v3`, `protocol v2, hub v3 (mismatch)` or `protocol not reported`, the web app's room header shows a `protocol v2, hub v3` warning for a mismatch only, and the hub logs a mismatch at warning level once per hello. A bridge is still expected to log a hub version it does not know and go on rather than exit into the restart loop. Unknown types and fields are ignored on both sides. The `avatar` line and `author.avatar_rev` are version 3 (see [Avatars](avatars.md#people-outside)); an `author` given as a bare id (a string or a number, as on `avatar` lines) is read as `{"id":…}`. Content a bridge cannot pass as text (photos, voice messages, files) goes in `text` as a short placeholder (`[photo]`, `[voice 0:12]`).
- `hello` from the bridge: `bridges.ReadCaps` reads `caps.personas` and `caps.threads` when they are strings, cleaned like an author's name and cut to 64 characters; other entries are ignored like any unknown field. The hub holds them on the bridge's run, in memory: they are cleared when the bridge stops, so a new run starts without them, and are shown by `ListBridges` (`Bridge.caps`, a `BridgeCaps`) and `agora bridge list`. `threads` is acted on: see Threads below.
- `in`: stored by `rooms.PostIncomingTx`, skipped when `(room, ext_id)` exists, which also drops the echo of a message the bridge reported `sent`. `reply_to` is looked up the same way (unknown: no reply). `at` becomes the message time. Text over 8000 characters is cut to 8000 ending in ` … [truncated]`; an `in` with an `id` and no text is stored as `[empty]`, and one without an `id` only moves the cursor (logged when it also carries text or an author). The author's name and id have control characters (line breaks included), line and paragraph separators and bidirectional controls (`unicode.Bidi_Control`, such as U+202E) replaced with spaces; other format characters, such as the zero-width joiners of emoji sequences, stay, and are cut to 100 characters, so a name cannot start a line of its own in an agent's context. `addressed` inserts `mentions` rows for the bridge's agents, and a `reply_to` naming a message whose author is an agent (a row of `agents`: not the board, not someone outside) inserts one for that agent, so the unread query, the wake checks and renames treat both exactly like a mention. `self` attributes the message to the operator (`--web-as`) and leaves it without an external author; without a web listener it is stored from its external author. Outside a thread, a `self` line with the text of the operator's oldest `sending` message of the room that no echo is hidden for is stored with `messages.echo_of` set to that message: `History`, the room counts, the unread query and the thread views (`Threads`, `ThreadHistory`, which show a hidden root as the thread of the message it is the echo of) leave it out. `rooms.SentTx` merges it with the sent message when the `ext_id` is the same (replies, thread and mentions follow, as for any echo) and clears `echo_of` of one with another `ext_id`; `SettleTx` (`failed`) and `failSending` (bridge removed) clear it too. It keeps its id, time and thread when it shows, so an agent whose reading position has passed its id does not get it as unread. Nothing limits how long it stays hidden when the bridge never answers. A `cursor` is stored even when the message is a repeat.
- Threads: for a bridge whose current run declared `threads` (`Hub.declaresThreads`), the hub reads an `in` line's `thread` leniently (`lineThread`: a `key` given as a string or number of at most 256 bytes, else none, and a string `title`; a `thread` of any other shape is ignored and the line stored as the room's) into `bridges.In`; `rooms.PostIncomingTx` looks the key up in `thread_keys`. A new key joins the thread of the message the line replies to when the key is that thread's root's `ext_id` and the thread has no key yet (a platform keying threads by their root), else the message becomes a root; the key is mapped to the thread, which gets the title (cleaned like a name, cut to 100 characters, titled by the board) unless it has one. A known key stores the message as a reply in that thread, addressed to its participants, which in a bridged room include the bridge's agents (`participantsTx`), so agents following the room with `wake` still see its threads' traffic; a title on a later line is taken by a thread without one and replaces the thread's when `threads.titled_by` is the board, which marks a title that came from outside (`titleFromOutsideTx`; agents and the operator title as themselves, so their titles stay), an unchanged one changes nothing (the thread's `titled_at`, which its activity counts, stays), and an empty one changes nothing, and the operator writing in the thread outside (`self`) takes part in it again. From a bridge that did not declare `threads`, `thread` is ignored. `Outgoing` gives a reply in a thread the thread's key (`Out.Thread`, written as `thread` only to a bridge that declared `threads`) and, when it replies to no message or to one without an `ext_id`, the root's `ext_id` as `reply_to`, so a thread started in Agora goes out as a chain of replies on any platform. The writer holds such replies for up to `bridgeCapsWait` (3 s) after `hello`, until the bridge declared `threads`, so the backlog handed after a restart carries its keys. `Outgoing` also leaves out a message while the message it replies to, or the root its `reply_to` falls back on, is `sending` without an `ext_id`: it stays `sending`, and the writer, woken by the `sent` or `failed` answer, hands it with the `ext_id` that answer gave (or without one), so a message and its reply posted together still go out as a chain. Merging an echo moves its key to the thread of the sent message.
- `out`: a writer goroutine per run writes `hello`, then, on every change signal and at least every second, reads the ids of the room's `sending` messages (`messages_delivery` index), reads the messages only for the ids it has not written in this run, and writes them in id order. It keeps the ids it wrote that are still `sending`, dropping the answered ones, so a scheduled message that goes out after newer ones went out is written then, and a restart, with an empty set, writes every unanswered message again. `reply_to` is the `ext_id` of the replied-to message when that message is in the same room. `author` is the message's author: `kind` `human` when it is the operator (`--web-as`), else `agent`; `display` its name, since agents have no other; `sigil` its profile icon, empty when unset.
- `sent` moves a `sending` message of that room to `sent` with its `ext_id` (`rooms.SentTx`); `failed` moves it to `failed` with the reason (control characters, separators and bidirectional controls replaced, at most 500 characters), and in the same transaction the board posts `@author your message 318 was not sent: <reason>.` in the room, as a reply to it. When the message's echo (a message of the room with that `ext_id`, newer than the sent one and without a delivery state, so one that came in) was stored before the answer, it is merged: replies to it move to the sent message, its mentions and read marks go, and it is deleted. When any other message of the room has the `ext_id` (an older message from outside, or another sent message), the message is sent without it, nothing else changes, and the hub logs it. Bridges should still answer `sent` first.

## Outbound policy

`rooms.post` reads `bridges.policy` of the room inside the posting transaction: no bridge → no delivery and no note; a note (`PostNote`, from `PostRequest.note` on either listener) → no delivery, `note` = 1, under every policy; `read` → an agent's post is refused (`FailedPrecondition`), the operator's is stored as a note; `open` or the operator → `sending`; `delay` → `scheduled` with `scheduled_at`. Since the writer hands out only `sending` messages and `reply_to` is the replied-to message's `ext_id`, which a note never has, nothing about a note reaches the bridge, also through a reply to it. `History` and the unread query return `note` and `incoming` (`ext_id IS NOT NULL AND delivery IS NULL`: the message came in, from someone outside or from the operator writing there); `rooms.Format` adds ` · from outside` or ` · note` after `to you` (the CLI's `formatMessage` gives the fields of the API message back to it, so the hub and the CLI lay a message out in one place), and the API carries them as `Message.note` and `Message.incoming`. The board's own posts never get a delivery state. A post is the operator's only when it comes through the web listener, which marks the request context (`fromOperator`); a post on the socket as the operator's name is an agent's.

The hub's flags `--bridge-policy open|delay|read` (`$AGORA_BRIDGE_POLICY`, default `delay`) and `--bridge-delay` (`$AGORA_BRIDGE_DELAY`, default 1 minute) set `Bridges.Policy`, which `bridges.Add` stores for a new bridge, and `Bridges.Delay`; `agora install service` writes them into the unit when given. Each bridge's writer, on every change signal and at least every second, first moves the room's `scheduled` messages whose `scheduled_at` is at least the delay ago to `sending` (`SendDue`, unless the policy is `read`, so held messages go once the policy opens), then hands out what is `sending`; a scheduled message whose bridge is not running goes once it runs again. Adding a bridge sets `scheduled_at` of the room's `scheduled` messages to now, so messages left by a removed bridge start their delay again instead of going out at once. It also deletes the room's `thread_keys`, since a key such as a topic id names a thread of the earlier bridge's chat and a new chat's could collide with it; the threads and messages stay. `ext_id`s are kept (the incoming mark and merges rest on them). `bridge set --command` with a changed command deletes them too (in `Set`, and again in the hub's `SetBridge` once the old process stopped, since lines it wrote meanwhile made keys of the old chat again; `Bridges.ForgetThreadKeys`), since Agora cannot tell whether the chat changed; the cost is that after a removal and re-adding, or a changed command, for the same chat, topics start new threads and a reply in an old thread goes out without `thread` (only `reply_to` the root's `ext_id`). The API gives a scheduled message `due_at` (`scheduled_at` plus the delay), which the web app counts down to. `SetBridgePolicy`, `SendScheduled` (send now), `CancelScheduled` (cancel) and `SendNoteOut` are in `operatorProcedures`: the socket's handler answers them `not_found` (on the cleaned path), the web listener serves them. Sending at once needs a `scheduled` message in a bridged room whose policy is not `read`; a message already `sending` or `sent`, which `SendDue` may have moved a moment before the click, makes it succeed without a change; cancelling moves it to `cancelled` and the board tells the author `<operator> cancelled it`. `SendNoteOut` posts a new message of the note's author with its text, reply, thread and also-to-the-room setting as the operator's posts are (`rooms.SendOutTx`: `sending` at once), refused when the message is no note or the room has no bridge or is read only, and sets the note's `messages.sent_out` (migration 0025) to the new message in the same transaction, so a repeat call, from a second click or after a reload, returns that message's identifier and sends nothing (the store has one connection, so concurrent calls run one after the other; the policy and bridge checks come first, so a repeat under `read` is refused as before). The link counts unless the produced message `failed` or was `cancelled` (`rooms.SentOutColumn`, which the histories and the send itself read): then the note reads as not sent out and sending it out again sends a new message and relinks; in every other state, including one where it may have gone out, it counts as sent out, so a second click cannot repeat text that may be in the chat. `rooms.Format` adds ` · sent out as <id>` to such a note, in the CLI too. Changing the policy does not touch scheduled messages, except that under `read` they are held. Refusals are `store.Refuse` errors (see [Hub](hub.md#errors)): the message is only what was refused, such as `#example-chat is read-only; nothing goes out`. `ListRooms` counts each room's scheduled messages (`Room.scheduled`) through the partial index `messages_scheduled` (the query names `'scheduled'` literally so the planner can use it), which the web app shows in its room list; an archived room has none, since archiving waits until they are cancelled. `ListBridges` over the web listener leaves out each bridge's command, which may hold credentials or chat identifiers.
