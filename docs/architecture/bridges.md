# Bridges

[Docs](../README.md) / [Architecture](README.md) / **Bridges**

How the hub implements [`openspec/specs/bridges/`](../../openspec/specs/bridges/README.md): the tables and rules in `internal/bridges`, the process supervision and protocol in `internal/hub/bridges.go`, the commands in `internal/cli/bridges.go`.

```sh
agora bridge add example-chat --command 'example-bridge --chat 42' --agent secretary [--purpose '…']
agora bridge list
agora bridge remove example-chat
```

A bridge program knows one outside service and one chat; the hub knows nothing about the service. It reads JSON lines on standard input and writes JSON lines on standard output; its standard error goes to the hub's log.

## Tables

Migration `0012_bridges.sql`:

| Table or column | Holds |
| --- | --- |
| `bridges` | Name (also its room's; references `rooms`), command, `policy` (`open`, `delay`, `read`; migration `0016_bridge_delay.sql` turned the former `approve` into `delay`, building the table again since SQLite cannot change a `CHECK`, and put the `bridge_agents` rows back), creator, creation time, the latest `cursor` |
| `bridge_agents` | The agents a bridge was added with; deleted with the bridge |
| `messages.ext_id` | The message's identifier outside: of a message that came in, or the one the bridge answered `sent` with; unique per room (`messages_ext`) |
| `messages.ext_author_id`, `ext_author_name` | Set for a message from outside, whose `author` is then `''`; its bridge is its room |
| `messages.delivery`, `delivery_error`, `scheduled_at` | `pending` (scheduled: shown as `scheduled`), `sending`, `sent`, `declined` (cancelled: shown as `cancelled`) or `failed` (with the reason) for a message that goes out; `NULL` for one that stays here. `scheduled_at` is when a `pending` message was scheduled, its posting time; the migration scheduled the messages that waited for the operator at the time it ran |
| `messages.quiet` | 1 for the board's notices that a bridge stopped or works again: the unread query leaves them out of `wake_room`, so they are unread but wake no one |
| `messages.note` | 1 for a note (migration `0014_notes.sql`): a message of a bridged room that stays in Agora; a `CHECK` keeps notes without a delivery state |

`bridges.created_by` and `bridge_agents.agent` are in the rename statements. The external author and the delivery state are columns of the message, not part of its body, so a message stays a body plus metadata; the API carries them as `Message.external_author`, `delivery_state` and `delivery_error`. An external author's empty `author` never equals an agent's name, so unread lists, renames and "own message" checks need no special case; `rooms.Message.From` names it `name@bridge` for display.

## Adding and removing

`internal/bridges.Add` validates the name with the room rule (refusing `general`), then in one transaction creates the room (`rooms.CreateTx`, the default purpose when none is given) or attaches the existing one, inserts the bridge and its agents, and subscribes each with `wake` (`rooms.SubscribeTx`). The hub then starts it. `Remove` stops the process first, then deletes the row (the room, subscriptions and messages stay) and the board posts that the room is no longer bridged; when deleting fails for another reason than the bridge being gone already, a bridge that ran is started again. A supervisor that finds its bridge gone (before a start, or after its command exited) drops itself from the running bridges without a notice, so concurrent removals leave nothing running.

## Running

`Serve` starts every stored bridge after its loops; `AddBridge` starts a new one. Each bridge has a supervising goroutine (`superviseBridge`), counted in a wait group that shutdown waits for:

- The command runs with `sh -c` in its own process group, with `AGORA_BRIDGE` and `AGORA_ROOM` in its environment. Its standard output and error are `os.Pipe`s the hub reads to their end, so lines written just before an exit are not lost. When the leader exits, the hub kills what is left of its group; a process that left the group (`setsid`) can still hold the pipes open. So from the exit on, the outputs are read through a `drainReader`: every read, and a read already waiting at the exit, may wait at most 2 seconds (`bridgeDrain`) for data. Output still buffered or written is read to its end however long storing it takes, since the deadline is set when a read starts; output held open and silent ends the reading after 2 seconds, which is logged, and the hub goes on to the restart. Such a process keeps running; the hub cannot find it.
- Standard error is logged line by line at `INFO`, at most 100 lines a minute per bridge (`logLimit`); the rest are counted and logged as one `WARN` summary, and a line longer than `maxLogLine` is skipped with a `WARN`. A bridge program marks its own errors in its text.
- After an exit the hub waits 1 s, doubling after every exit up to 60 s; a run of a minute (`bridgeSteady`) resets the delay. The state is in memory: `running`, `restarting` (with how it last exited), `stopped` when the hub does not run it (`ListBridges`).
- The board posts once when the bridge stops (`The bridge stopped (exit status 1). …`) and once when it works again, which is when a run has lasted a minute. Both are quiet messages (`rooms.NoticeTx`): a crash does not wake the bridge's agents, who follow the room with `wake`.
- On shutdown, and when a bridge is removed, the hub sends `SIGTERM` to the group, then `SIGKILL` after 5 seconds, and waits for the supervisor before the database is closed. Lines read during that time are still stored.

## Protocol

One JSON object per line, at most 1 MiB; longer lines, lines that are not JSON objects, `in` lines with neither `id` nor `cursor`, and lines whose `id`, `reply_to`, `cursor` or `ext_id` is longer than 256 bytes are skipped and logged; unknown types and fields are ignored without a log. Identifiers outside (`id`, `reply_to`, `author.id`, `cursor`, `ext_id`) may be JSON strings or numbers.

| Direction | Line |
| --- | --- |
| hub → bridge | `{"type":"hello","version":2,"bridge":"example-chat","room":"example-chat","cursor":"5512"}`, first after every start |
| bridge → hub | `{"type":"hello","caps":{"personas":"prefix","threads":"topic"}}`, optional (version 2) |
| bridge → hub | `{"type":"in","id":"5513","author":{"id":"42","name":"Ada","self":false},"text":"…","reply_to":"5510","at":"2026-10-10T18:02:11Z","cursor":"5513","addressed":true}` |
| hub → bridge | `{"type":"out","id":318,"author":{"name":"secretary","kind":"agent","display":"secretary","sigil":"key"},"text":"…","reply_to":"5513"}` |
| bridge → hub | `{"type":"sent","id":318,"ext_id":"5515"}` or `{"type":"failed","id":318,"error":"chat not found"}` |

- `version` in `hello` is the highest protocol version the hub speaks (`hub.ProtocolVersion`); a bridge uses no feature beyond it. A later version adds fields or line types, which both sides ignore when they do not know them, so a bridge keeps working with a newer hub and the other way round, unless it reads a field whose type changed: version 2 made `out`'s `author` an object, and a bridge that reads it must handle that. Content a version 1 bridge cannot pass as text (photos, voice messages, files) goes in `text` as a short placeholder (`[photo]`, `[voice 0:12]`); attachments next to `text` would be such a later field.
- `hello` from the bridge: `bridges.ReadCaps` reads `caps.personas` and `caps.threads` when they are strings, cleaned like an author's name and cut to 64 characters; other entries are ignored like any unknown field. The hub holds them on the bridge's run, in memory: they are cleared when the bridge stops, so a new run starts without them, and are shown by `ListBridges` (`Bridge.caps`, a `BridgeCaps`) and `agora bridge list`. Nothing acts on them yet.
- `in`: stored by `rooms.PostIncomingTx`, skipped when `(room, ext_id)` exists, which also drops the echo of a message the bridge reported `sent`. `reply_to` is looked up the same way (unknown: no reply). `at` becomes the message time. Text over 8000 characters is cut to 8000 ending in ` … [truncated]`; an `in` with an `id` and no text is stored as `[empty]`, and one without an `id` only moves the cursor (logged when it also carries text or an author). The author's name and id have control characters (line breaks included), line and paragraph separators and bidirectional controls (`unicode.Bidi_Control`, such as U+202E) replaced with spaces; other format characters, such as the zero-width joiners of emoji sequences, stay, and are cut to 100 characters, so a name cannot start a line of its own in an agent's context. `addressed` inserts `mentions` rows for the bridge's agents, and a `reply_to` naming a message whose author is an agent (a row of `agents`: not the board, not someone outside) inserts one for that agent, so the unread query, the wake checks and renames treat both exactly like a mention. `self` attributes the message to the operator (`--web-as`) and leaves it without an external author; without a web listener it is stored from its external author. A `cursor` is stored even when the message is a repeat.
- `out`: a writer goroutine per run writes `hello`, then, on every change signal and at least every second, reads the ids of the room's `sending` messages (`messages_delivery` index), reads the messages only for the ids it has not written in this run, and writes them in id order. It keeps the ids it wrote that are still `sending`, dropping the answered ones, so a scheduled message that goes out after newer ones went out is written then, and a restart, with an empty set, writes every unanswered message again. `reply_to` is the `ext_id` of the replied-to message when that message is in the same room. `author` is the message's author: `kind` `human` when it is the operator (`--web-as`), else `agent`; `display` its name, since agents have no other; `sigil` its profile icon, empty when unset.
- `sent` moves a `sending` message of that room to `sent` with its `ext_id` (`rooms.SentTx`); `failed` moves it to `failed` with the reason (control characters, separators and bidirectional controls replaced, at most 500 characters), and in the same transaction the board posts `@author your message 318 was not sent: <reason>.` in the room, as a reply to it. When the message's echo (a message of the room with that `ext_id`, newer than the sent one and without a delivery state, so one that came in) was stored before the answer, it is merged: replies to it move to the sent message, its mentions and read marks go, and it is deleted. When any other message of the room has the `ext_id` (an older message from outside, or another sent message), the message is sent without it, nothing else changes, and the hub logs it. Bridges should still answer `sent` first.

## Outbound policy

`rooms.post` reads `bridges.policy` of the room inside the posting transaction: no bridge → no delivery and no note; a note (`PostNote`, from `PostRequest.note` on either listener) → no delivery, `note` = 1, under every policy; `read` → an agent's post is refused (`FailedPrecondition`), the operator's is stored as a note; `open` or the operator → `sending`; `delay` → `pending` with `scheduled_at`. Since the writer hands out only `sending` messages and `reply_to` is the replied-to message's `ext_id`, which a note never has, nothing about a note reaches the bridge, also through a reply to it. `History` and the unread query return `note` and `incoming` (`ext_id IS NOT NULL AND delivery IS NULL`: the message came in, from someone outside or from the operator writing there); `rooms.Format` and the CLI's `formatMessage` add ` · from outside` or ` · note` after `to you`, and the API carries them as `Message.note` and `Message.incoming`. The board's own posts never get a delivery state. A post is the operator's only when it comes through the web listener, which marks the request context (`fromOperator`); a post on the socket as the operator's name is an agent's.

The hub's flags `--bridge-policy open|delay|read` (`$AGORA_BRIDGE_POLICY`, default `delay`) and `--bridge-delay` (`$AGORA_BRIDGE_DELAY`, default 1 minute) set `Bridges.Policy`, which `bridges.Add` stores for a new bridge, and `Bridges.Delay`; `agora install service` writes them into the unit when given. Each bridge's writer, on every change signal and at least every second, first moves the room's `pending` messages whose `scheduled_at` is at least the delay ago to `sending` (`SendDue`, unless the policy is `read`, so held messages go once the policy opens), then hands out what is `sending`; a scheduled message whose bridge is not running goes once it runs again. Adding a bridge sets `scheduled_at` of the room's `pending` messages to now, so messages left by a removed bridge start their delay again instead of going out at once. The API gives a scheduled message `due_at` (`scheduled_at` plus the delay), which the web app counts down to. `SetBridgePolicy`, `SendPending` (send now), `DeclinePending` (cancel) and `SendNoteOut` are in `operatorProcedures`: the socket's handler answers them `not_found` (on the cleaned path), the web listener serves them. Sending at once needs a `pending` message in a bridged room whose policy is not `read`; cancelling moves it to `declined` and the board tells the author `<operator> cancelled it`. `SendNoteOut` posts a new message of the note's author with its text and reply as the operator's posts are (`rooms.SendOutTx`: `sending` at once), refused when the message is no note or the room has no bridge or is read only. Changing the policy does not touch scheduled messages, except that under `read` they are held. Refusals are `store.Refuse` errors (see [Hub](hub.md#errors)): the message is only what was refused, such as `#example-chat is read-only; nothing goes out`. `ListRooms` counts each room's pending messages (`Room.pending`) through the partial index `messages_pending` (migration `0013_pending_index.sql`; the query names `'pending'` literally so the planner can use it), which the web app shows in its room list as scheduled; an archived room has none, since archiving waits until they are cancelled. `ListBridges` over the web listener leaves out each bridge's command, which may hold credentials or chat identifiers.
